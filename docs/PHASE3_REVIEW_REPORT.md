Also built:

- **`ArchitectureViewPage`** (`src/pages/ArchitectureViewPage.tsx`): the shared page shell (domain tabs, header, canvas, drawer, `?node=` deep link) that both the Total Architecture page and every deep dive now render through — one code path, seven views.

- **`DomainDeepDivePage`** (`src/pages/DomainDeepDivePage.tsx`) + `/architecture/:domain` route: resolves the URL segment to the right curated view, redirects to `/architecture` on an unknown segment.
- **Cross-links** (`src/data/viewIndex.ts`): a reverse index, built from the seven view objects themselves (never a hand-maintained list), from a canonical catalogue id to every view that renders it. `SystemDetailDrawer` and `GapDetailDrawer` now show a "Shown in architecture views" section linking straight to `<view>?node=<id>` for every system or gap that appears in one or more diagrams.
- **10 new vendor logos** added to `src/components/logo/brandIcons.ts` / `src/data/curatedView.ts`'s `DEEP_DIVE_LOGO_ADDITIONS` for focus systems that never appeared in the Total Architecture: Elo, Vercel, Meta, Salesforce, Anaplan, Google, Kronos, Snowplow (simple-icons or wordmark, decided the same way as the Phase 0 audit), plus Algolia and Cloudinary (simple-icons, added this phase — real path/hex data copied from the installed `simple-icons@16.28.0` package, same CC0-sourced, no-runtime-fetch approach as the original 6).
- **Generalized validator** (`scripts/validate-layout.ts`): now runs the full 13-rule deterministic check (unique ids, referential integrity, canvas bounds, edge orthogonality, card/gap limits, logo coverage, catalogRef resolution, node/group overlap, node-in-group containment, edge–label/edge–node/edge–edge intersection) against **all 7 views**, not just the Total Architecture.
- **`tests/e2e/deep-dives.spec.ts`**: the same golden-path checks Phase 1 wrote for the Total Architecture (every node/group renders, node count matches, gap count ≤ the view's own `maxVisibleGaps`, 11px font floor, no card scrollbars, every vendor logo renders, drawer opens/closes), parameterized over all 6 deep dives, plus a tab-navigation test.
- **`tests/e2e/privacy.spec.ts`** extended: the stakeholder/CGI-name regression guard now checks all 6 new routes too, not just the Phase 1/2 set.

## 2. Gap-mapping audit (viewManifest → real research_gaps)

`fullResearchCatalogue.viewManifest` specifies each deep dive's `focusSystems` (real `component_id`s) and `requiredGaps` (free-text phrases) with status `"to-curate-after-total-view-approval"` — a specification, not pre-built data. A naive keyword-match script against the 64 `research_gaps` titles produced several **wrong** matches (verified by manually reading the full gap list), so every mapping below was corrected by hand.

**Fully matched** (Store & Checkout: 8/8, Digital Experience: 8/8, ERP & Supply: 7/7):

- Store & Checkout — target POS/SCO→GAP-001, POS computer→GAP-003, scanner→GAP-004, receipt printer→GAP-005, scales→GAP-006, payment terminal hardware→GAP-007, CCTV/loss-prevention→GAP-009, field service→GAP-010.
- Digital Experience — commerce engine→GAP-015, OMS→GAP-016, inventory promise→GAP-017, returns orchestration→GAP-018, e-commerce fulfilment/3PL→GAP-019, PIM/MDM→GAP-020, DAM→GAP-021, customer identity→GAP-012.
- ERP & Supply — target planning vendor→GAP-027, range/assortment→GAP-028, WCS/WES→GAP-030, MHE/robotics→GAP-031, voice picking→GAP-032, warehouse devices→GAP-033, carrier EDI→GAP-035.

**Partially matched, with an explicit skip** (no fabricated gap record was created — per the data model's own "Do not infer" research principle):

- Data & Customer Intelligence (5/6) — data governance/catalog→GAP-046, observability→GAP-047, AI/ML operating model→GAP-048; **MDM ownership** and **real-time event ingestion** reuse GAP-026 and GAP-042 from other domains (both are genuinely cross-cutting: an enterprise MDM hub and an event-streaming backbone matter to data intelligence even though their `domain_id` is `DOM-ERP`/`DOM-INTEGRATION`). **"Authoritative data lake/lakehouse topology" has no corresponding gap record anywhere in the dataset and was skipped.**
- People & Service Management (4/6) — recruitment ATS→GAP-036, endpoint management→GAP-050, managed-service partners→GAP-058. **"Identity source of truth"** and **"HR integration layer"** both plausibly describe the same single record, GAP-038 ("HR-driven identity lifecycle"); it was mapped to "identity source of truth" as the closer fit, leaving **"HR integration layer" unmatched** rather than double-counting one record as two gap cards. **"Service monitoring" has no corresponding gap record and was skipped.**
- Integration, Cloud & Security Foundation (9/10, using 10 gap records) — iPaaS/ESB→GAP-040, API management→GAP-041, event streaming→GAP-042, MFT→GAP-043, IAM/SSO/PAM→GAP-049, EDR/XDR→GAP-051, SIEM/SOC→GAP-052, observability→GAP-045; "SD-WAN and Wi-Fi" is one compound phrase covering **two** real records, GAP-053 (SD-WAN/WAN) and GAP-054 (store/DC/office Wi-Fi) — GAP-011 ("store network / SD-WAN / Wi-Fi") was deliberately **not** reused here since it's the store-specific variant of the same concern, not the enterprise-wide one this view is about. **"Cloud security posture" has no corresponding gap record and was skipped.**

**Isolated nodes** (rendered with zero edges inside a given deep dive, because their only real `architecture_edges` point at components outside that view's focus-system scope): `customer-identity` (digital), `range-assortment` (erp-supply, no edges anywhere in the dataset), `next-ai` / `firebase` / `master-data-hub` / `event-streaming` (data-intelligence), `endpoint-mdm` / `managed-service-partner` (people-service), `azure` / `iam-pam` / `sdwan` / `wifi` (foundation-security). None of these edges were invented to avoid an isolated-looking card.

## 3. Bugs found and fixed while building this phase

- **Three node-height overflows clipped the status badge.** `sc-adyen`, `es-wuunder` and `dc-salesforce-signal` all combine a wordmark logo (which eats more horizontal space than a simple-icons mark, forcing an extra title line) with a long real display name, and the original heights (90–100px, matched to shorter neighbours) left the `StatusBadge` partially or fully clipped below the card's bottom edge. Caught by screenshot review, not by the geometry validator (card overflow is a CSS/visual concern, not a layout-geometry one) — a reminder that the deterministic checks and visual review catch different bug classes. Fixed by increasing each node's `h` (100→120, 100→130, 90→130) and re-routing the 2 edges whose waypoints assumed the old, shorter card boundary (`sc-e04`, `sc-e07`, `es-e12`) so they still clear the taller cards without crossing anything else.
- **Iterative edge-routing conflicts caught by the validator during authoring** (all fixed before this report, listed for the record since the process is the actual deliverable, not just the result): edges that legitimately needed to route past several sibling cards to reach a hub or a distant "TO FIND" target (`digital-commerce`'s `dc-e07`/`dc-e08`/`dc-e09` reaching Contentstack and OMS around the group boundary and label text; `erp-supply`'s `es-e11`/`es-e12` reaching SAP EWM/TM around the label and around each other) needed 2–4 rounds of `npx tsx scripts/validate-layout.ts` → read the failing rule → move one waypoint, exactly the audit-then-fix loop used in Phase 0/1. No deviation was shipped that the validator still flags.

## 6. Deviations / known limitations

- The legacy `fullResearchCatalogue.architecture_views` / `architecture_groups` / `view_nodes` / `view_edges` structure (9/35/287/239 records) was **not** used as a starting point for any deep dive, even though it superficially resembles pre-built view data. It is a filter-derived structure — exactly the anti-pattern `CLAUDE.md` prohibits — so every view in this phase was authored from scratch against `viewManifest.focusSystems`/`requiredGaps` and the real `architecture_edges`/`research_gaps` records instead.
- 5 required-gap phrases across 3 domains have no corresponding `research_gaps` record and were not force-mapped (see §2): "authoritative data lake/lakehouse topology", "HR integration layer", "service monitoring", "cloud security posture". A future research pass that adds these gap records can slot new gap cards into the existing groups without relayout.
- Digital-commerce's and data-intelligence's isolated nodes (§2) show 0 connectors by design; a future phase that finds the real integration (e.g. what actually authenticates `CMP-CUSTOMER-IDENTITY`) should add the edge to the existing node, not restructure the view.

## 7. Statement on later phases

Phase 4 (research/editing workflow — creating/updating sources, claims, gap status transitions, CSV import) and Phase 5 (Postgres/Supabase persistence, authentication, RLS) remain **deliberately not built**.
